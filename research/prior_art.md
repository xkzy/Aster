# Aster prior-art review (living, not yet comprehensive)

**Review cutoff:** 2026-11-12. **Status:** active; this is an evidence-based interim review, not a final exhaustive survey. Full text was fetched/read for the most directly overlapping work where linked below. Other families are tracked in `novelty_matrix.md` with explicit review status. Search snippets are leads, not evidence. Publication metadata is taken from publisher/proceedings or author primary sources when available.

## Interim answer: three closest research directions

### 1. Automated C/C++ to memory-safe Rust migration

This is the closest *end-to-end migration* line. It spans materially different approaches:

- **C2Rust** is a compatibility-oriented C→Rust transpiler whose output commonly retains raw pointers and `unsafe`; **Laertes** starts from that output and uses compiler-guided search/refactoring to remove some raw pointers.
- **Crown** analyzes C2Rust Rust MIR and retypes some raw pointers using ownership inference. Its key ownership-monotonicity result (Theorem 2) is local: pointer assignment preserves unique ownership under its stated assumption. The paper does not prove whole-translator semantic preservation; its implementation admits underconstrained idioms and the authors describe it as theoretically neither sound nor complete for the full input space.
- **C2SaferRust** (IEEE TSE 2026; arXiv manuscript first appeared in 2025) combines C2Rust, static dependency/context analysis, LLM slice rewrites, and compiler/test feedback. It reports *reductions* in raw pointers/unsafe lines, not elimination, and checks tests rather than proving safety/equivalence.
- **Scylla** translates a structured C subset directly to safe Rust using a type-directed translation, split-tree analysis for pointer arithmetic, and mutability inference. Its OOPSLA 2026 paper says the steps are formalized on paper but that it has *no formal guarantee* of translation correctness; it relies on tests and iterative source refactoring.
- **Cpp2Rust** (PLDI 2026) translates a supported C++11 subset into safe Rust while using runtime `Rc<RefCell<T>>`/pointer wrappers to preserve aliasing/mutability behavior, then optimizes the wrappers. The paper gives a trace-refinement argument and unit/differential tests, not a mechanically checked translator proof. Its measurements vary sharply by workload: about 2% penalty on WOFF2 compression, but up to 6× slower on Brunsli.

These works already establish that restricted C/C++ migration, ownership recovery, safe target generation, and post-translation optimization are active research topics. Aster cannot claim novelty merely for translating C/C++ to safe source, inferring ownership, or optimizing runtime guards.

### 2. Ownership, borrowing, and lifetime inference

Rust’s borrow checking is a source-language-specific static discipline. **Oxide** formalizes a Rust-like ownership/borrow core and proves type safety for that calculus; it is not a cross-language inference algorithm. **Crown**, **Laertes**, and the LCTES 2024 C borrow-checker prototype adapt related constraints to C translation/checking. **Morphic** (OOPSLA 2026) introduces a *new pure functional language* with automatic borrow/lifetime inference and reference counting as fallback; it gives a heap semantics and memory-safety soundness theorem and reports benchmark-specific gains over Perceus. That substantially narrows any claim that automatic borrow inference plus a cost/performance motivation is new, while not solving C++ object lifetime, C pointer provenance/UB, Python identity, or cross-language migration.

### 3. Semantics-aware, cost-sensitive representation/type inference

**CCured** (TOPLAS 2005) performs whole-program pointer-kind inference and explicitly chooses qualifiers to minimize runtime-check overhead while retaining its safety guarantees. **&inator** (PLDI 2026) encodes semantic-equivalence/type-correctness constraints, including Rust borrow-checking rules, and selects precise, least-cost Rust *interfaces* for C declarations using Z3. It does not generate whole function bodies; its definition of correctness is that a semantics-preserving safe Rust implementation exists for the inferred interface. It reports superlinear constraint-solving costs, reaching hours on programs of a few thousand lines, and documents unsupported C features. Earlier Java ownership inference also defines a best-typing objective (ECOOP 2012), although its objective is ownership-tree quality, not execution cost. **Perceus** and **Morphic** cover reuse/RC/borrow tradeoffs. Thus neither a weighted objective, “joint” inference, nor reuse/copy minimization alone is novel.

## Cross-cutting question status

### Unified ownership inference across C, C++, Rust, and Python

**Not established by the work reviewed so far.** The closest tools are pairwise or language-specific (especially C/C++ to Rust). Earlier ownership inference also exists for C/C++ leak checking and Java ownership-type annotations (Clouseau, OwnKit, and ECOOP 2012 best-typing inference), so the claim cannot be framed as the first cross-language ownership inference without a narrower, verified scope. This is a search result, not a proof of absence. A common IR could encode heap locations, capabilities, lifetimes, and effects, but it cannot erase source semantics: C undefined behavior/provenance and pointer arithmetic; C++ constructors/destructors, exceptions, aliasing and object identity; Rust moves, drops, lifetimes and unsafe blocks; Python arbitrary object identity, dynamic dispatch, aliasing, finalizers and runtime integer semantics. A sound “unified” method needs source-specific semantic adapters and a precisely bounded common fragment. An IR alone is not a contribution.

### Python compilation/specialization is not ownership migration

The Python side has important compiler baselines, but the reviewed systems answer different questions. Cython and mypyc compile source modules to C extensions while retaining CPython integration; Nuitka compiles through C/C++ and supports CPython-based modes; Numba specializes supported functions with JIT/type inference and distinguishes nopython from object execution; PyPy traces an interpreter at runtime; Codon compiles a Pythonic subset/DSL. These approaches can change representation or avoid some Python object work, but they are not evidence of a cross-language ownership inference algorithm or of a memory-safe Aster translation. They retain runtime/semantic boundaries or restrict the accepted language. The detailed review is incomplete for several papers; see the matrix.

### Static memory safety without inserted checks vs zero runtime overhead

These are separate claims. **Aster itself has no `unsafe` construct or escape hatch.** Its current accepted language contains only scalar values and scalar operations; it has no pointers/references, arrays, allocation, deallocation, or FFI. Thus no memory-unsafe operation is expressible in the current subset, but this is not evidence for memory-safe ownership inference over heap-manipulating programs. Future claims must be derived from the whole accepted Aster language, static checker, and backend—not by assuming a Rust-like `unsafe` mode exists.

For comparison, safe Rust’s ownership discipline provides compile-time rejection for its accepted safe subset, but ordinary runtime costs (allocation, destruction, bounds checks, overflow/panic behavior) may remain. Checked C and CCured use gradual/runtime mechanisms where static analysis does not discharge obligations. Cpp2Rust explicitly moves alias/mutability enforcement to runtime wrappers and then removes some checks. Therefore “no inserted runtime memory-safety checks” and “same performance as an optimized native-source baseline” are distinct hypotheses; neither follows from the other. Aster must report instrumentation and runtime/cost measurements separately.

(The current scalar-only Aster boundary is specified in [`docs/spec/aster-safety.md`](../docs/spec/aster-safety.md).)

### Minimal-modification migration

Compiler-diagnostic-guided iteration, ownership-directed rewriting, structured-C refactoring, and cost-sensitive interface choice already exist. Aster needs an explicit edit-cost definition and a baseline, not a general claim that automation minimizes edits. Separate mechanical edits, semantic redesign, annotations, proof obligations, and review time.

### Proof-guided optimization

CompCert, VST-Floyd, RefinedC, RustBelt, Aeneas, symbolic Rust borrow-checking, translational verifier soundness, translation validation, LLVM attributes, borrow inference, and reuse analyses provide substantial prior art. Proof-derived facts can enable optimization, but producing a proof or using a type-system fact is not itself novel. A candidate must identify an optimizer decision or proof artifact unavailable to a strong composition of existing analyses and show the difference experimentally.

## Strongest current research lead (not yet a contribution)

A plausible direction to investigate—not select yet—is a **machine-checkable, end-to-end translation certificate for a nontrivial C subset with inferred ownership**. Scylla has safe-target generation and useful pointer-arithmetic analysis but explicitly lacks a translation-correctness guarantee; Crown proves a local pointer-assignment ownership property but does not establish full translator soundness; &inator constrains interface types rather than translating bodies. However, CompCert, VST-Floyd, RefinedC, Aeneas, RustBelt, sound symbolic borrow checking, translational verifier foundations, and translation validation show that the component proof methods are mature. Simply adding an SMT check or proof certificate to a small translator may be incremental. The potential gap must be tested against these works and recent verified-Rust compilation before any implementation claim.
